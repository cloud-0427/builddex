# 启动事件采集与投递可靠性改造

状态：核心持久化与补传已实施；完整目标设计仍有待实施项。实际验证范围见第 9 节，不能将设计矩阵视为全部已通过。

本文承接 [03-startup-log-uploader.md](03-startup-log-uploader.md)。涉及持久化、上传开启时机、补传、首帧超时和统计口径时，以本文的目标设计为准；03 保留为既有阶段协议及历史实现说明。Stage 1–12 的编号不变。

## 1. 问题与证据

异常样本为剔除已收到 `FIRST_FRAME_DRAWN` 用户后的 489 人，不能直接称为 489 个实际启动失败用户。

按实际正常终态生成顺序，收到事件的用户数为：

| Stage | 1 | 2 | 4 | 5 | 6 | 7 | 8 | 9 | 10 | 3 | 11 | 12 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 用户数 | 489 | 429 | 365 | 310 | 266 | 224 | 196 | 165 | 147 | 126 | 100 | 0 |

- Stage 12 为零是筛选条件，不能用于证明首帧监听普遍失效。
- 已收到的阶段终态均为成功，不足以证明所有缺失处都实际失败。
- “有上一阶段、无下一阶段”的集合差不等于两列人数相减。例如 2→4 实际缺失 65 人，净下降 64 人，说明存在有 4 无 2 的用户。
- Stage 6 的网络授权 246 人与缓存授权 24 人合计超过 266；若各组均按用户去重，则有 4 人跨启动出现在两个组中，不能用用户级数据还原一次启动。
- 连续各阶段的下降与串行上传中断相容，但没有请求记录和 session 明细，不能据此量化真实失败率或认定网络为唯一原因。

当前代码的确定性问题：

| 位置 | 当前行为 | 后果 |
| --- | --- | --- |
| `JiaguStartupReporter.emit/scheduleDrain` | 仅 11 成功或 12 终态开启上传 | 早期失败事件入队后无法发送，真正早期失败甚至不进入上述样本 |
| `EARLY/QUEUE/drain` | 内存队列，单消费者，最多两次尝试 | 退出、网络失败后事件丢失，成功启动可能只收到日志前缀 |
| `markFirstLaunchCompleted` | 首帧生成时落首次完成标记 | 下一次不再采集，且没有历史补传，12 可能永久缺失 |
| 首帧监听 | resume 后才计时，超时使用主线程 | 无 resume 或主线程卡死时不能产生预期超时 |
| Native 提前返回 | 部分 JNI/分配/注入路径无失败终态 | 失败原因根本没有形成事件 |
| `StartupEventUploader.createBody` | session 字段被注释 | 服务端混合多次启动，无法可靠归因 |

Stage 3 是整个 attach 的结果，包围 4–10；失败时可以紧随失败子阶段出现，不要求所有前置阶段均存在。

## 2. 目标、边界与不变量

目标：可捕获失败留下稳定原因；进程退出后恢复待传记录；相同事件重试不重复计数；启动结果与投递结果分别统计。

不变量：

1. 事件先持久化，再具备发送资格；收到明确确认后才能删除。
2. 同一事件重传保持 eventId、sessionId、原始版本、发生时间及负载不变。
3. 正常 Stage 每阶段只有一个终态；内部检查点、超时观测及恢复诊断不伪装成新的 Stage。
4. 主线程和 Native 启动线程不执行网络请求；上报错误不能改变启动成功/失败、安全拦截行为。
5. 新事件采集资格与旧记录投递资格分离；非首次启动仍恢复并投递历史事件。
6. 不把无事件推断为某阶段 FAILED；无法解释的退出记为结果未知。

保证范围为“本地成功持久化后，在保留期内再次获得运行和网络机会时，至少一次投递，服务端幂等去重”。不承诺卸载、清数据、存储损坏、设备永久离线、不再启动或写入完成前被杀后的送达。所有本地写入也可能失败，必须有可观察的降级诊断。

## 3. 采集和持久化设计

### 3.1 早期初始化

将核心库加载移至 `ProxyApplication.attachBaseContext(base)`：调用必要的框架初始化后，先以 base 初始化壳内记录器、会话及存储，再生成 1 并加载核心库、生成 2，然后进入 Native attach。避免静态初始化失败时既无 Context 又无可恢复记录。

这是待验证的实现变更：确认没有其他路径提前调用 Native 方法，JNI_OnLoad、Reporter 类初始化没有循环依赖，反射创建 uploader 不会触发核心库提前加载。sessionId 每次进程启动生成；安装实例标识跨启动稳定。远程进程不创建主进程首次启动漏斗。

### 3.2 本地事件存储

建议采用 Android 平台 SQLite 的事务队列（无需新增业务依赖），存于应用私有、排除备份的目录。单写入协调器管理事件、检查点、首次完成状态；网络请求不得持有数据库事务或记录器锁。

最小数据模型：

| 表 | 关键内容 |
| --- | --- |
| sessions | sessionId、安装实例、原始版本、进程、采集资格、最近检查点、已知启动结果 |
| outbox | eventId 主键、不可变事件负载、原始 sessionId、PENDING/IN_FLIGHT、尝试次数、下次重试时间、租约 |
| diagnostics | 隔离的不可重试记录、清理计数、写入错误计数；容量受限，不保存敏感正文 |

生成事件时以短事务提交事件与相关检查点。首帧成功事件和首次完成标记必须在同一个事务提交，不能仅落完成标记却没有待传 12。持久化失败时保持启动行为，记录本地降级原因；不能声称事件可靠保存。

为保证已提交记录可恢复，正常阶段事件采用短同步写入，网络完全异步。即将抛异常或 `_exit` 的路径必须先尝试提交失败记录；不等待 HTTP、不循环重试磁盘写入。同步磁盘 I/O 不等于零延迟，必须以性能门槛验收，存储异常也不得取消安全退出。当前普通终止路径可以执行落盘；不得在异步 native signal handler 中调用 Java、SQLite 或非 signal-safe API。

建议初始限额：总记录 1,024 条、负载总量 4 MiB、保留 7 天；均为待性能验证的配置值。清理先移除过期/已确认记录，再淘汰普通成功事件；优先保留 FAILED、BLOCKED 和首帧结果。容量强制上限仍可淘汰高优先级记录，必须计数，不能宣称永不丢失。清理不删除当前 session 的必要恢复检查点。schema 升级需事务迁移，禁止不兼容时直接清空待传数据。

## 4. 投递、确认与补传

初始化恢复队列后即可启动独立 worker，不依赖 Stage 11 成功。uploader、网络库及传递依赖必须位于壳 DEX；用最终加固 APK 验证，不能仅凭源代码依赖声明判断。

生命周期：`PENDING → IN_FLIGHT → 服务端确认 → 删除`；失败返回待传或隔离。发送进程退出后，租约到期或确认旧进程已结束，将遗留 IN_FLIGHT 恢复。事务中领取记录，事务外上传；禁止两进程同时重复领取无保护记录。重复发送仍由服务端幂等兜底。

- 启动时恢复、网络重试定时器唤醒均可触发发送；不依赖业务初始化成功。远程进程默认不启动发送者，存储层仍需防御并发访问。
- 优先发送失败/拦截及首帧结果，其余按发生顺序并给予公平调度，防止历史或当前 session 饥饿。服务端不得把接收顺序当执行顺序。
- 无网络、超时、408/425/429/5xx：持久化退避时间，采用带抖动的指数退避，基准 1 秒，上限 15 分钟；尊重合法 Retry-After。达到单次运行尝试预算后暂停，不删除事件，下次继续。
- 400/422 等负载问题进入有界隔离区；401/403/404 等配置问题暂停该目标发送并保留记录至有效期，避免全队列反复撞错。
- 未配置远端 uploader 时明确为本地诊断模式，禁止把默认 Logcat 输出认作远端 ACK 并清空远端待传队列。

服务端协议必须在实施中与接口维护方确认，不能假设现有接口支持：

| 项目 | 目标协议 |
| --- | --- |
| 事件身份 | 稳定 eventId；同一次生成只创建一次，重试复用 |
| 关联 | schemaVersion、runtimeVersion、package/version、sessionId、startupInstanceId、processName、isMainProcess、isFirstLaunch |
| 内容 | stageId、stage、status、resultCode、事件类型、发生时间、单调 elapsed、session 内 sequence |
| 兼容 | 保留现有 event/eventId/itemName 映射；现有 eventId 是阶段编号，新唯一 ID 使用独立字段 telemetryEventId，禁止直接改变旧字段语义 |
| ACK | 确认具体 telemetryEventId 已接收；重复已接收也可确认；未知 409 不视为成功 |
| 批量 | 可选升级，逐条返回 ACK；只删除已确认项，未确认项保留 |

若当前单条接口仅有 HTTP 2xx，必须明确其代表已可靠接收还是仅网关成功，以及业务响应体错误语义，再实现确认解析。服务端先上线唯一事件字段与去重，客户端随后启用持久化重试。批量不是首版客户端可靠性的前提。

事件不得包含密钥、token、credential、服务端响应正文、完整异常堆栈和原始 Activity 类名。诊断允许稳定原因码和白名单异常类别；历史补传不重新采集设备信息覆盖原事件归属。

## 5. 完整阶段观测与首帧状态机

### 5.1 Native 和恢复诊断

逐一枚举每个 JNI_CHECK_NULL、ExceptionCheck、return 和 `_exit`：已进入阶段的可捕获失败均产生唯一 FAILED/BLOCKED；子阶段失败后 Stage 3 可产生汇总 FAILED，但根因归属子阶段，不重复统计两个失败 session。

ClassLoader 注入函数返回明确结果，验证实际注入成功后才报告 Stage 9 SUCCEEDED。Application 构造、绑定、attach、onCreate 分别覆盖异常。存在 pending JNI exception 时先保存受限信息并正确处理异常，再报告，禁止以 pending exception 状态调用上报并假装成功。

持久化当前活动阶段和最近成功检查点。Stage 3 包围 4–10，应保存活动子阶段，不能只写单个“3”。后续启动确认旧 session 不再活跃且没有结果时，生成独立 `PREVIOUS_STARTUP_INCOMPLETE` 诊断，关联原 session 和发现它的新 session；不生成伪造的旧阶段 FAILED，不将正常后台进程结束误判为启动崩溃。

### 5.2 首帧

`FIRST_FRAME_DRAWN` 保留现有 OnPreDraw 语义：观察到绘制前回调，不等价于已显示到屏幕或业务数据就绪。不得混用更强的“实际呈现帧”指标而不升级协议。

状态为 `WAITING_RESUME → WAITING_PREDRAW → DRAWN`。Stage 11 成功后安装生命周期监听并启动独立 watchdog；记录安装失败，不能只捕获 DecorView observer 安装失败。watchdog 与上传 worker 分离，防止网络阻塞拖延超时。

首版建议 10 秒阈值，可配置并用单调时钟计算。无 resume 时产生等待 Activity 的诊断；后台启动或启动意图未知时，不自动把无 Activity 判为失败。resume 后无 PreDraw 或主线程卡住时记录超时观测。首帧监听直到成功、明确结束或清理上限仍可工作，生命周期切换/销毁应移除旧监听并记录原因。

为解决“超时后迟到成功”与单终态冲突，目标协议采用：**超时是独立诊断事件，不竞争 Stage 12 终态**；Stage 12 SUCCEEDED 仍在真正观察到 PreDraw 时生成，安装监听不可恢复失败可生成 Stage 12 FAILED。超时诊断具有独立 eventId 和 diagnosticCode，最多一次；迟到成功附带 lateAfterTimeout。服务端分别统计超时发生和最终成功，避免超时覆盖成功或两个 Stage 12 终态。该语义须由 schemaVersion 区分，不能无版本地改变旧 FIRST_FRAME_TIMEOUT 报表。

如果 session 在超时后退出且无成功，恢复记录为结果未知并附超时证据，不伪称观察到了崩溃。后台无界面启动可记不适用/未知，不能触发首次首帧完成标记。

## 6. 验证体系

### 6.1 分层和测试设施

1. JVM 单测：终态竞争、事件 ID 稳定、退避/分类、集合统计与协议序列化。使用可注入单调时钟、随机源和调度器，禁止靠长 sleep 验证。
2. Android instrumentation：真实 SQLite 事务、重启恢复、多进程争抢、首次标记原子性、生命周期及主线程阻塞。需要设备/模拟器外部控制进程死亡与重启，不能把内存对象重新创建当进程重启测试。
3. 最终加固 release APK 集成：R8 后壳依赖闭包、JNI 方法、真实 Application、Native 故障注入及低版本兼容。
4. HTTP 合约测试：MockWebServer 或等价本地服务控制状态码、响应体、断连、ACK 丢失、重试和批量部分确认；不访问生产 endpoint。

故障注入仅存在于测试构建，使用确定性编号触发；生产 APK 静态检查必须不存在注入开关/入口。Native 无法安全复现的资源错误使用测试分配器/JNI 包装器注入，不以耗尽真实设备内存作为常规 CI 手段。

每个用例同时检查：本地 outbox/session 状态、实际发送请求、mock 服务端去重后记录、业务生命周期结果。仅断言 Logcat 或 upload 被调用不算投递验证。

### 6.3 自动化门禁与回归执行

- 每次 PR：协议/队列状态机/退避/统计单测、编译和格式检查；修改 Native 返回路径时更新故障映射清单，逐条关联用例。
- 每日集成：设备上的数据库、生命周期、HTTP 合约及进程重启测试；失败保留 APK、版本、设备/API/ABI、随机种子、故障编号、脱敏本地状态和请求轨迹。
- 发布候选：R01–R28 全量执行，批量未启用时仅 R20 可标不适用并注明；关键杀进程窗口 R14–R16 各重复 100 次，已提交事件恢复和幂等断言必须全部通过。
- 设备矩阵覆盖项目声明的最低 API、代表性中间 API、最高已验证 API，以及每种发布 ABI；增加实际用户量较大的厂商 ROM 和低内存设备。确切 API/机型由发布测试清单锁定，不以“最新版”作为可复现条件。
- 每个线上缺陷先新增可复现夹具/故障用例，再修复；未稳定通过的关键可靠性用例不得简单标记 flaky 跳过。
- 以上为新增门禁计划，具体 Gradle task 和 CI job 名称在实现时落地，不能将现有单元测试通过等同于已满足本矩阵。

### 6.4 性能与可靠性验收

相同 APK 配置、设备、授权缓存和网络条件，分别测旧实现与新实现。冷启动至少 100 次，缓存授权与网络授权分别统计；用独立外部测量/本地计时验证，不依赖正在改造的上传链路自身。

建议初始发布门槛（实施前固定基线，调整须记录依据）：

- 主线程网络调用为零；无新增启动崩溃、ANR、安全绕过。
- 壳 attach 与首帧耗时的新增 P95 均不超过 `max(20ms, 基线 P95 的 5%)`；单次正常事件持久化 P95 ≤ 5ms。低端设备达不到时重新评估持久化策略，不能悄悄删除关键落盘。
- 在可控测试中，已提交且未过期/未触发容量淘汰的事件，网络恢复并给予足够执行时间后 100% 收到 ACK；服务端去重后重复数为零。
- 队列容量符合配置，失败重试不造成无界线程、CPU 或磁盘增长；记录负载上限与 SQLite 文件/WAL 实占分别测量，不能仅以负载量声称数据库物理大小受同一限制。
- 首帧迟到、队列失败、磁盘失败均不改变原有业务启动行为。

## 7. 上线与报表回归

先上线服务端兼容字段、ACK 和幂等，再发布客户端。按固定版本/渠道灰度 1%→10%→50%→100%；每档至少观察 24 小时，并等到受控补传窗口有足够已恢复网络的样本。具体样本门槛发布前锁定，样本不足不得以零错误通过。

上线观察：明确 FAILED/BLOCKED 数、收到事件数、ACK 数、待传积压/最老年龄、重试/隔离/TTL/容量清理数、同 session 有后无前比例、首帧成功迟到补传数，以及启动 P95、崩溃、ANR。失败事件增加可能是观测恢复，不能直接当作业务回归；与独立崩溃及性能数据交叉验证。

报表按 schema/runtime/version/channel 分层，先按 session 聚合，再按安装实例聚合；记录发生时间与接收时间分别保留。按固定观察窗口（建议 24 小时）展示暂定结果，补传后允许修订；过期后缺失仍不等于失败。

| 分类 | 证据 |
| --- | --- |
| 首帧成功 | 12 SUCCEEDED/FIRST_FRAME_DRAWN，包括超时后迟到成功 |
| 明确失败/拦截 | 同 session 的 FAILED/BLOCKED；汇总 Stage 3 不重复计数根因 |
| 超时观测 | 有 watchdog 诊断，最终成功/失败另外统计 |
| 结果未知 | 缺终态、恢复发现未完成，或启动意图不明；不推断崩溃 |
| 待补传 | 仅客户端队列或额外诊断可证明；服务端单凭缺事件不能认定 |

首次启动尝试成功率以收到 1 的同口径 session 为分母、这些 session 中收到 12 成功为分子，同时报告未知比例及样本仅覆盖可观测 session 的限制。若以 2 成功作分母，指标必须命名为“核心库加载后首帧成功率”。用户级最终成功率另算，不混用。

出现新启动崩溃/ANR、关键用例违反不变量或性能超门槛即停止扩量。回滚必须保留可读的 outbox schema；通过兼容补丁暂停 worker/新特性而不删除待传数据。配置开关需本地可用，不能依赖启动成功后才能获取远端开关。回滚前后执行 R14、R15、R23，防止回滚本身清掉证据。

## 9. 首批实施记录

已实现：

- `StartupEventStore` 使用 noBackup 目录 SQLite、FULL 同步模式，先事务保存事件再由单一 worker 上传。上传期间不删除记录，进程退出可重放；仅主进程发送，当前实现不引入跨进程发送者或租约。
- Stage 12 成功与首次完成标记在同一事务中保存；读取旧 SharedPreferences 完成标记兼容升级，新版本使用数据库标记。非首次启动仍恢复旧 outbox。
- 核心库在 attachBaseContext 中、记录器初始化后加载；不再等待 Stage 11 成功才发送。
- 可重试失败保存退避和次数，不因两次失败删除；不可重试及损坏记录隔离。7 天、1,024 条和约 4 MiB 负载限制，清理优先保留失败/拦截/首帧记录。
- 快照序列化保留历史事件字段；增加 telemetryEventId 和 Idempotency-Key，恢复上传 sessionId/startupInstanceId，旧 eventId 仍为阶段编号。
- 默认 Logcat uploader 不确认删除待传记录。自定义 uploader 正常返回意味着确认，失败必须抛异常。

实际验证：运行时 JVM 单测通过；示例 app Java 编译通过；Samsung SM-G990U2 / Android 14 的真实 SQLite instrumentation 测试通过（关闭重开、延迟重试、原始元数据、去重插入和确认删除）。另通过两个不同 PID 的 instrumentation 验证 Reporter：首进程产生 1 和 12、保存首次完成状态，不上传；force-stop 后新进程初始化并补传两条旧事件，保持原 session，且不采集新的非首次事件。测试接收器为本地回调，不访问生产服务。

可复现命令（项目根目录，PowerShell）：

```powershell
.\gradlew.bat :jiagu-runtime:testDebugUnitTest :jiagu-runtime:connectedDebugAndroidTest :app:compileDebugJavaWithJavac
.\gradlew.bat :jiagu-runtime:assembleDebugAndroidTest '-Pjiagu.runtimeTestRunner=io.github.xjc.jiagu.RestartProbeInstrumentation'
adb install -r jiagu-runtime/build/outputs/apk/androidTest/debug/jiagu-runtime-debug-androidTest.apk
adb shell am instrument -w -e phase seed io.github.xjc.jiagu.test/io.github.xjc.jiagu.RestartProbeInstrumentation
adb shell am force-stop io.github.xjc.jiagu.test
adb shell am instrument -w -e phase replay io.github.xjc.jiagu.test/io.github.xjc.jiagu.RestartProbeInstrumentation
```

seed 仅重置独立测试包内的 outbox，不能针对生产包运行；期望 seed/replay 均 PASS 且 PID 不同。

剩余边界：示例 HTTP uploader 暂沿用原有 2xx 确认语义，尚未验证服务端业务 ACK/去重；未实现批量、跨进程租约、Native 全路径错误补齐、独立首帧 watchdog、活动检查点、完整性能及 R8 后 APK 回归。重传可产生重复远端事件，直到服务端支持新唯一 ID 去重。设备标签等请求外层信息仍在上传时获取，事件快照内部的 session/version/时间保持原值。当前隔离/清理仅有本地诊断，持久化计数和配置错误全局暂停仍待补齐。磁盘写入失败时记录本地错误并保持启动，不承诺该事件可补传。旧内存队列已经丢失的历史数据无法恢复。
