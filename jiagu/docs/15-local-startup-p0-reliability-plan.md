# Local 启动事件 P0 可靠性与缺口归因方案

日期：2026-10-16。状态：客户端核心已实施；实际验证与剩余范围见 [实施和回归记录](16-local-startup-p0-implementation-and-regression.md)。本文保留目标设计，不能据此认定服务端或完整设备矩阵已验收。

适用范围：`jiagu-local-runtime` 的本地 Payload 加载与可选事件上报。延续真实 Application、公开 AppComponentFactory 和平台 API 路线，不引入旧 Native Runtime、在线授权或业务启动依赖。

## 1. 目标与保证范围

P0 目标是：统一启动统计口径；尽可能保留早期失败；实现可恢复投递；在受控断网、杀进程、重启、重复投递测试中，让每个事件缺口都有可核对的证据归属。

“解释缺口”不等于证明每次退出的真实原因。必须区分以下三种承诺：

1. 已成功持久化的事件，在保留期内再次获得进程运行及网络机会时，持续尝试投递，服务端去重后只计一次。
2. 可捕获异常尽力在重新抛出原始异常前提交失败记录；记录器不能改变业务成功、失败或安全校验结果。
3. 任意指令处强杀、OOM、存储故障、系统崩溃不能保证留下完整记录。受控测试由外部控制器记录注入位置；生产环境缺乏确证时归为“结果未知”，并保留最后检查点及证据等级。

不承诺卸载、清除数据、设备永久离线、不再启动、未完成写入或存储损坏后的送达。应用被 force-stop 后不承诺后台自动运行，测试必须显式再次启动。不得把未知补写为失败，也不得补造缺失的历史成功事件。

3. **1001→7 净缺 40**：区分 GCM 认证、摘要校验、内存分配、其他解密异常及未知中断。
4. **1002→1003 净缺 26**：分别观察 native library 路径构造与 ClassLoader 构造；按系统、ABI、机型、版本和耗时聚类。
5. **1001/7/1002 间其余缺口**：补查 DEX 表、header、长度与边界错误。
6. **1004/1005/1006**：分别查看 Provider 初始化、Uploader 构造、Application onCreate、界面启动资格；1005 与 1006 只做关联观测，不计算严格串行流失。

已有数据只能依据现有明细归因；没有 session 或原始日志的历史缺口不能由此次改造追溯补齐。

## 4. 无新增第三方依赖的实现结构

采用 Android/JDK 平台能力：`java.io`、`java.nio.channels`、`CRC32`、`SQLiteDatabase`、`JSONObject`、`ScheduledThreadPoolExecutor`、`HttpsURLConnection`。不新增 Room、WorkManager、OkHttp、协程、崩溃 SDK 或 Native 库；不引入隐藏 API。

分为两层持久化：

- **早期 journal**：ClassLoader 创建前可使用，只保存有界元数据，不依赖 Context、业务类或 uploader。
- **正式 SQLite outbox**：Provider 初始化后接管，导入 journal，管理重试、确认、恢复和诊断。

网络始终在后台。早期留证需要少量同步磁盘写入，这是可靠性与启动耗时的明确取舍，必须测量；禁止用“全异步落盘”宣称任意强杀可恢复。

### 4.1 早期存储入口及实现门禁

在 `instantiateClassLoader` 的加载入口，用系统提供的 `ApplicationInfo.dataDir` 定位应用私有目录；不依据解密后的包名、配置或外部输入拼接任意路径。设置独立目录 `jiagu-startup-v1`，在 Manifest 的适用备份/迁移规则中明确排除此目录，并验证 API 29/34/36 及 direct-boot 场景。Provider 获取 Context 后验证路径与应用私有存储归属一致。

该路径需要在目标系统上验证可创建、可写、权限与存储域正确，不能仅凭设计认定成立。锁定态无法写入时降级为内存并记录可恢复的存储诊断，不借用隐藏 Context、不切换到公共存储。若无法通过真机验证，此项 P0 不得宣称已完成。

每个进程会话使用 UUID 命名独立 journal，避免多个进程共享追加文件；维护进程存活锁，文件锁异常时禁止推断旧 session 已死亡。journal 归并需独立领取锁，进程存活锁与领取锁职责分离。先建立 session/header，再提交 STARTUP_ATTEMPT；没有成功 header 的启动属于采集边界外，受控测试控制器仍要记录。

事件由壳类直接编码，禁止触发业务 ClassLoader、反射 uploader 或额外网络初始化。telemetry 关闭时不创建日志、不启动线程，保持现有可选配置语义。

### 4.2 journal 格式与崩溃一致性

使用版本化追加帧：`magic | formatVersion | length | payload | crc32`。长度先校验，单帧初值上限 8 KiB；payload 包含完整事件或内部检查点。禁止 Java 原生对象序列化。

一次逻辑记录在同一帧表达事件与阶段状态，写完调用 `FileDescriptor.sync()`；返回成功后才记为已提交。CRC 仅检测截断/损坏，不作为身份认证。解析只接受完整合法前缀，尾部半帧隔离并计数，禁止信任损坏长度分配大数组。

正常流程记录：会话开始、阶段 ENTER、阶段终态，以及下一个阶段 ENTER。相邻终态和 ENTER 可以合并在同一帧，但须在实际进入下一阶段前提交。进程在两者之间被杀时只能称“边界中断”，不能认定下一阶段已执行。

不逐字节刷盘；帧数与大小有上限。失败路径只尝试一次短写和 sync，不循环抢救、不等待 HTTP；sync 没有平台通用硬超时保证，必须记录耗时并做慢存储验证。无法接受的 I/O 尾延迟需调整保证范围并重新验收，不能静默改为异步。

### 4.3 journal 导入 SQLite

Provider 初始化时恢复旧 journal，也导入当前 session 的完整帧；读取过程与同进程追加通过锁协调，只取稳定合法前缀。

每批导入在 SQLite 事务中按 telemetryEventId 幂等插入事件、按 session+sequence 幂等应用检查点，并提交导入偏移。只有数据库提交完成后才允许推进 journal 清理状态。导入后崩溃、重复导入不得重复计数。

活跃 journal 不删除；旧 journal 只有确认导入完成、所属进程不再存活后才可删除。文件保留与数据库确认各自独立：journal 已导入不代表事件已被服务端接收。

schema 升级使用事务迁移，禁止升级时清空待传数据。未知格式保留有界隔离记录并产生兼容诊断。

## 5. 会话、事件与存储模型

### 5.1 事件身份与冻结规则

保留 JSON `eventId` 为旧阶段编号，新增能力不改变 1/7/1001～1006 的成功语义。真正唯一键始终为 `telemetryEventId`；Java 现有 `eventId` 成员虽为 UUID，接入时也必须防止与 JSON 同名字段混淆。

新协议建议 schemaVersion=4，由服务端先兼容，字段如下：

| 字段 | 规则 |
| --- | --- |
| sessionId | 每个进程启动一次 UUID；历史补传保持原值 |
| telemetryEventId | 生成一次并持久化；重试、重启、重复导入不重建 |
| sequence | 同 session 严格递增，涵盖阶段记录和诊断；允许因写入失败出现缺号，不伪造连续性 |
| recordType | STAGE / DIAGNOSTIC；检查点可为内部记录，不伪装新增成功阶段 |
| event/eventId/status/resultCode | 阶段名、阶段编号、显式状态和稳定结果码；保留 itemName 兼容字段 |
| occurredAtMillis / elapsedMs | 原发生时间和进程内单调时钟偏移；接收时间由服务端另记 |
| runtimeVersion/buildId/package/version | 从构建生成的壳内静态元数据获得，解密失败也能归属原版本 |
| processName/isMainProcess | 最早入口采集；无法确认则标 UNKNOWN，不冒充主进程 |
| launchContext | FOREGROUND_CONFIRMED / BACKGROUND_CONFIRMED / UNKNOWN，必须注明来源 |
| relatedSessionId/diagnosticCode | 恢复诊断关联旧会话；诊断本身属于发现它的新会话 |

安装实例 ID 可在私有目录生成一次，仅用于分析且不作为事件主键；并发创建须用锁与原子提交，不使用 OAID 作为会话身份。默认不增加设备标识采集。

事件业务负载一旦持久化保持不可变。禁止重试时改写版本、发生时间、进程或设备快照。诊断到达、尝试次数等投递状态另存。现有示例在发送时读取的 productInfo 版本等也需要冻结或明确为传输时信息，服务端以事件原始版本为准。

### 5.2 SQLite 表建议

| 表 | 核心字段与约束 |
| --- | --- |
| sessions | sessionId PK，原版本/进程，activeStage，lastSuccess，lastSequence，knownOutcome，lastCheckpointAt |
| outbox | telemetryEventId PK，sessionId，sequence，immutablePayload，state，attempts，nextAttemptAt，leaseOwner，leaseUntil |
| stage_records | sessionId+stage+status 类别去重；成功和失败终态竞争必须产生冲突诊断，不能悄悄覆盖 |
| diagnostics | code，关联 session/event，证据来源，计数；禁止异常 message/敏感正文 |
| imports | journalId PK，committedOffset，formatVersion |
| retention_audit | 淘汰原因、时间、数量、受影响 session 的有界索引及归因范围 |

sessions 检查点和相应事件在同一事务提交。恢复不能因先更新检查点、后插入失败事件而生成相互矛盾的状态。SQLite 使用平台支持的事务与可靠同步设置；具体 journal_mode/synchronous 组合通过真机断进程验证确定，禁止仅依赖默认参数作保证。

## 6. 投递、确认与恢复

### 6.1 状态机

`PENDING → IN_FLIGHT → ACK 后删除`；临时失败回到 PENDING；不可重试负载进入 QUARANTINED；目标配置问题进入暂停状态并保留记录。

事务内领取、事务外 HTTP、事务内确认。IN_FLIGHT 使用租约和 owner，重启后回收失效租约；多个进程不能重复无保护领取。P0 只由主进程发送，其他进程保留独立 journal，主进程恢复导入。

重试使用持久化指数退避及抖动，建议基准 1 秒、上限 15 分钟，尊重有上限的合法 Retry-After。达到本轮尝试预算只暂停本轮，不删除记录。计时处理设备时间回拨和异常未来时间，防止队列永久冻结。

启动恢复和进程内定时器均触发 drain；可选使用平台网络回调提前唤醒，不新增权限之外的业务依赖。无进程运行机会时不保证发送，不为此引入常驻服务或 WorkManager。

### 6.2 错误分类与 ACK

| 结果 | 行为 |
| --- | --- |
| 网络异常、断连、超时、408/425/429/5xx | 保留并重试 |
| 400/422 等确定的负载拒绝 | 隔离该事件；留下拒绝类别，避免堵住后续事件 |
| 401/403/404 等目标配置错误 | 暂停目标；保留队列，配置修复后继续 |
| 2xx | 只有已确认契约代表服务端持久接收才可删除 |
| 409 | 只有服务端明确确认同 telemetryEventId 已接收才视为 ACK |
| ACK 不匹配、响应不合法 | 不删除，记录协议诊断 |
| 本地 ACK 删除失败 | 独立重试本地事务；若进程死亡导致重传，服务端幂等兜底 |

服务端先上线唯一键及持久接收后确认能力，推荐返回明确 telemetryEventId。现有 2xx 契约须由接口维护方核实，不能把网关接收等同于事件已入库。批量不是 P0 前置条件。

服务端对同 key 同内容重复返回成功，对同 key 不同内容返回冲突并告警；去重范围包含租户/产品，保留期至少覆盖客户端最长补传期及网络重试余量。HTTP Idempotency-Key 请求头本身不构成幂等保证。

### 6.3 容量与淘汰

建议初始上限：journal+数据库逻辑负载总计 4 MiB、1024 条事件、7 天保留；物理文件及 WAL 大小另设监测和维护策略。数值须按启动频次及真机开销调整，不视为已验证值。

优先清理已确认与过期数据，再淘汰普通成功事件，尽量保留失败与未完成会话检查点。上限不足时允许有审计地淘汰任何类别，不承诺失败永不丢失。审计区有独立小额预算且不递归为每次日志失败生成无限日志。

受控验收在上限内执行，必须逐事件对账；额外容量测试验证被淘汰事件可解释。若仅剩聚合审计、无法定位单条事件，则只能声称“范围内发生淘汰”，不能宣称逐条已解释。

## 7. 尽可能记录失败

### 7.1 阶段覆盖

| 位置 | 必须记录的证据 |
| --- | --- |
| 最早加载入口 | session/header、启动事件；路径不可写时的内存降级状态 |
| asset 读取及外层配置 | missing/duplicate/长度/格式/包名/配置错误；1001 仍代表读取和外层配置检查完成 |
| 解密及摘要 | 认证、摘要、分配、其他解密结果；不记录密钥、nonce、密文或明文 |
| DEX 解析 | 表、header、边界错误及当前阶段 |
| nativePaths / ClassLoader | 两个内部 substep；公开 1003 成功边界不变 |
| Application 构造 | 默认和 AndroidX 工厂均记录成功或原始失败类别 |
| Provider/Reporter 初始化 | 无配置、非主进程跳过、Context 不适用、监听注册失败、Uploader 构造失败，使用独立诊断 |
| Activity 回调 | 监听安装时间、首次 resumed；无回调保留等待状态 |

Application attach/onCreate 不在现有工厂回调可完整包围的范围内。P0 不引入 ProxyApplication 或反射 hook 来伪装覆盖。建议提供无依赖的显式业务接入点，由真实 Application 在 onCreate 开始、结束、异常处调用；未接入标记“不可观测”。

默认不安装全局 UncaughtExceptionHandler；可选后续接入必须保留原处理器行为，并不能承诺捕获所有 native crash/OOM。可选利用平台 ApplicationExitInfo 提供退出佐证时，区分系统版本支持与证据匹配置信度；它不是 P0 必须依赖，也不能仅凭时间接近认定精确根因。

### 7.2 故障隔离

所有记录器调用边界捕获自身异常，重新抛出的仍为原业务异常。记录失败不能置阶段为业务失败，不能放行原应拒绝的 Payload。持久化成功后再更新内存去重状态；失败时保留降级标志，避免一次写失败导致后续永远不再尝试留证。

OOM 时不拼装大 JSON、不保存堆栈；使用预先准备的简短记录缓冲尽力写一次，不能保证成功。只上传稳定结果码、允许的异常类别及有限数值，不上传任意 exception message、凭据、完整堆栈或 DEX 内容。

后续启动发现旧 session 无终态时生成 PREVIOUS_STARTUP_INCOMPLETE 诊断，保存最后 ENTER/成功/投递状态。只有确认旧进程已结束才做此判断；时间超限和 PID 相同/不同都不能独立证明存活状态。

## 8. 缺口归因与统计规则

### 8.1 固定样本与集合

以 Asia/Shanghai 的 10 月 15 日 session 启动发生时间固定样本，按产品、buildId、schemaVersion、主进程和采集配置分层。收集之后数日补传，分别提供即时、T+1、T+7 视图；这些是观察窗口，不是最终送达保证。时钟异常单列。

令 A 为样本内上一步成功的 session 集合，B 为本步成功集合，计算 `A\\B` 和 `B\\A`，并给出明细；相邻缺口比例为 `|A\\B|/|A|`。这与原表净差 `(|A|-|B|)/|A|` 不同。存在下游但缺上游时标采集/投递异常，不补造上游成功。

1005 与 1006 作为并行观测分支。1006 的成功率只在前台启动资格有明确证据的样本内计算；启动资格未知单列，不能直接把未 resumed 当后台或失败。

### 8.2 两轴归因

每个缺口同时记录“执行证据”和“投递证据”，避免把一次真实失败又因离线被重复当两次启动失败。

| 执行归属 | 判定证据 |
| --- | --- |
| CONFIRMED_FAILURE | 本阶段已提交 FAILED，含稳定结果码 |
| INTERRUPTED_UNKNOWN | 阶段 ENTER 后会话结束但无终态；真实原因未知 |
| NOT_REACHED | 已有更早的明确失败终态，按该路径不再执行后续阶段 |
| BOUNDARY_UNKNOWN | 最后成功后无下一 ENTER，无法确认下一步是否执行 |
| NOT_APPLICABLE | 有明确后台/非目标进程等资格证据 |
| INSTRUMENTATION_UNKNOWN | 存储/采集失败或完全没有足够执行证据 |

| 投递归属 | 判定证据 |
| --- | --- |
| PENDING/RETRYING | 本地事件存在、未确认；附最近错误及下次重试 |
| ACKED | 服务端持久接收确认；若报表缺失，继续检查分析链路 |
| QUARANTINED/PAUSED | 永久负载错误或配置暂停，有拒绝类别 |
| EVICTED/CORRUPTED | 有可关联清理或损坏证据 |
| DELIVERY_UNKNOWN | 本地及服务端证据不足，不能推定网络丢失 |

“受控注入强杀”是附加 TEST_CONTROLLER 证据，不向生产失败码伪装成 crash。报表每个 gapId 包含 session、阶段对、两轴归属、证据来源、证据时间和观察截止时间；后续补传允许更新归属并保留修订记录。

## 9. 受控测试与逐事件对账

测试使用 debug 专用故障注入及平台 HTTP 本地测试服务；不访问生产地址，不新增生产依赖。外部控制器保存 runId、buildId、设备、启动/强杀/重启时间、注入屏障、预期事件 ID；设备重启后仍保留控制器日志。Release 不含注入入口。

每次测试收集四份证据：控制器日志、journal 合法帧/损坏尾、SQLite sessions/outbox/diagnostics 快照、服务端原始请求及去重后数据库。另核对业务真实返回/异常/Activity 生命周期。Logcat 仅作辅助，不能替代持久化或接收证明。

| ID | 场景与注入位置 | 必须验证 |
| --- | --- | --- |
| R01 | 正常启动，网络正常 | 各阶段唯一终态；1005/1006 允许实际调度顺序；确认后队列清空 |
| R02 | 启动前断网，启动后恢复 | 已提交事件仍在；网络恢复后原 ID/原时间补齐 |
| R03 | 断网启动并杀进程，再联网显式重启 | 旧 session 原 ID 补传，新 session 不覆盖旧归属 |
| R04 | 每阶段 ENTER sync 完成后强杀 | 恢复到对应检查点；无终态标未知中断，不伪造 FAILED |
| R05 | 成功/失败终态 sync 后、发送前强杀 | 完整恢复原终态；明确失败仍归原阶段 |
| R06 | 帧写入中、sync 前强杀 | 合法前缀可读；半帧隔离；控制器证明提交窗口中断；不得承诺完整记录 |
| R07 | journal 导入事务提交前/后强杀 | 前者重导，后者幂等；不丢已提交帧、不重复事件 |
| R08 | 服务端已入库但 ACK 丢失 | 客户端重发同 ID；服务端唯一事件只有一条 |
| R09 | 收到 ACK 后、本地删除提交前强杀 | 允许重复 HTTP，服务端不重复计数 |
| R10 | IN_FLIGHT 时杀进程/设备重启 | 失效租约可恢复，不永久卡队列 |
| R11 | 主/远程进程并发及主进程恢复 | 独立 journal、不误判活跃会话、不交叉覆盖；非主进程不进入主漏斗 |
| R12 | asset 缺失/格式错误/认证错误/DEX 错误/类加载和 Application 构造异常 | 失败阶段及结果码正确；保留原异常；后续可运行版本恢复旧失败 |
| R13 | Provider/Uploader 初始化失败 | 独立诊断保留；不影响业务；修复后恢复待传 |
| R14 | 429/5xx/超时与 400/401/403/404 | 分别重试、隔离或暂停；不删除未确认记录；后续合法事件不永久饿死 |
| R15 | 后台启动、前台启动、1006 早于1005 | 资格有证据；并行事件不误判为漏斗失败 |
| R16 | 磁盘满、不可写、损坏帧、容量淘汰、时间回拨 | 降级不改变业务；可观测诊断/明确证据限制；无无限重试或错误大分配 |
| R17 | 旧版→新版升级后补传、不同版本混合 | 原版本不变；schema 可读；不混入新版本漏斗 |
| R18 | API 29/34/36，默认及 AndroidX 工厂，冷启动/锁定态 | 早期目录、备份排除、存活锁、恢复路径有效；最终加固 APK 验证 |

R04～R09 对每个关键阶段和事务边界执行，不只在 Activity 之后杀一次。故障 Payload 无法再启动时，用同签名、保留应用数据的修复包恢复；禁止卸载后声称补传成功。

测试通过条件：

1. 在存储正常、限额内，所有成功提交的 telemetryEventId 最终都能在服务端去重库找到；丢失数为 0。
2. 每个服务端 ID 仅一个逻辑事件；重试业务负载一致；同 ID 不同内容冲突数为 0。
3. 每个模拟报表缺口都有两轴归属及证据；强杀窗口可归未知，但必须与控制器注入位置一致。无证据的“网络原因”判定数为 0。
4. 每个注入可捕获异常均尝试留证；存储正常且提交成功时，恢复后的阶段/结果码与注入预期一致。
5. 模拟写入失败/半帧时准确标注保证边界；业务成功/失败与关闭 telemetry 的基准一致。
6. P50/P95/P99 启动耗时、同步写耗时、内存和文件大小有前后对比。性能门槛在实现前根据基线确定并记录，不能用无实测阈值宣称性能验收。

## 12. Payload 与 ClassLoader 本体优化（补充）

前面的 P0 主要解决可靠观测，不足以替代启动本身的性能及稳定性改造。本节直接针对当前实现，不把接收缺口率作为性能证据。所有项目均待实施；优先实施减少重复分配和扫描的改动，再评估协议及加载架构变更。

### 12.1 Payload 读取：减少大数组复制

当前 `LocalLoaderRegistry.read()` 将输入写入默认容量 ByteArrayOutputStream，再执行 toByteArray。对于大 Payload，缓冲区扩容可能多次分配并复制，toByteArray 还会再分配一份完整数组。读取结束后立刻分配明文 DirectBuffer，容易使加密数据、旧缓冲及明文内存的存活区间重叠。

建议第一批改为：

1. 对 ZipEntry.getSize() 先做非负、上限和可转换为 int 的校验，再按已知长度精确分配一个 byte[]。
2. 循环读取到预期长度，正确处理短读；提前 EOF 明确报截断，读满后确认没有额外数据。实际读取量与声明不一致必须拒绝，不截断后继续解密。
3. 未知长度走独立有界兼容分支，不能直接按 -1 分配；保留 MAX_ASSET、entry 方法、重复 entry 等现有检查。
4. 在最终 APK/AAB/splits 验证 Payload 的压缩方法，评估将 jgl 配为不压缩。密文通常压缩收益有限，避免额外 ZIP 解压；用真实包比较包体和读取耗时，不假设当前已采用 STORED。

预期收益：减少 Java 堆临时大数组和复制，降低 GC/分配压力。不能承诺减少多少毫秒或解决多少次启动失败，需看 Payload 大小和低内存设备实测。

不直接用 ZipFile.getEntry 替换当前重复 entry 检查：那会改变对歧义 APK 的拒绝行为。保留一次完整校验扫描，或将扫描结果与 nativePaths 共用，避免用牺牲校验换性能。

### 12.2 解密：控制峰值内存，保留校验语义

当前已直接解密到 DirectBuffer，DEX 通过 slice 引用同一明文区域，这条路线应保留；不改为每个 DEX 再复制一份 byte[]，也不落盘明文。

第一批可做：

- 结合精确读取减少密文临时副本；完成解密后缩短密文及配置临时引用的存活范围，禁止通过 System.gc 强制回收来优化启动。
- 将解密、摘要扫描、DEX 表解析、DirectBuffer 分配分别计时，观察低内存及大 Payload 下的峰值 Java/native 内存。不要把全部成本都归因于 AES。
- 失败清理保持密钥清零及明文清理；当前失败后逐字节 put 清零可比较固定小块覆盖写法，避免新建与明文等大的清零数组。须验证所有失败路径仍被清理且原始异常不被清理异常替换。
- 核对 retained 与 DEX slice 的引用关系，只保留加载器实际需要的数据；DirectBuffer 生命周期不能提前结束，不调用隐藏 cleaner 或强制释放。

第二批实验：比较当前一次性 doFinal 与分块 update/doFinal 并同步计算摘要。某些平台 Provider 在 GCM 认证前可能缓存数据，分块 API 不自动等于流式低内存。必须通过认证成功后才交给 DEX 解析和 ClassLoader；认证失败的任何中间明文不得被使用。

禁止直接去掉 SHA-256、GCM、DEX header/边界检查，禁止切换到固定指定加密 Provider 或增加第三方加密库作为未经验证的“优化”。修改摘要或容器协议需另行设计和版本化，不进入第一批。

### 12.3 ClassLoader：先优化构造前的 nativePaths

当前 1003 的计时同时包含 nativePaths(info) 和 InMemoryDexClassLoader 构造，不能据此认定都是 ART 创建加载器慢。

`nativePaths()` 当前对 base/split APK 的每个候选 ABI 执行 Collections.list(zip.entries())，重复枚举并构造 entry 列表。第一批改为每个 APK 只扫描一次中央目录，将实际 native ABI 记入小集合，再按进程支持 ABI 的既有顺序选择；直接遍历 Enumeration，不构造全量 entry List。

进一步将主 APK 的 Payload 查找、重复检查及 native 库目录识别合并为一次 ZIP 扫描；通过内部读取结果传递 native 路径元数据。路径在当前 session 缓存，保持 APK 更新、split、32/64 位隔离和失败后不回退原 ClassLoader 的语义。无需持久化跨版本路径缓存。

分别记录 ZIP 打开/扫描、路径拼接、InMemoryDexClassLoader 构造耗时。如果主要时间在 ART 内部，Java 侧调整扫描只能改善其中一部分，不能声称优化了整个构造过程。

不直接删除 APK 内 native 路径而只保留 nativeLibraryDir；这可能破坏未提取 JNI 库和 ABI split。所有路径改动都需普通 APK、配置 splits、解压/未解压 JNI、32/64 位设备与真实 JNI 加载验证。

### 12.4 暂不采用的架构变更

不在主线程等待后台解密来声称异步启动：框架需要先取得 ClassLoader，仍会等待。ClassLoader 创建也不适合直接推迟到首次 Activity 后，因为 Application、Provider 可能已经依赖业务类。

不直接落盘解密 DEX、持久化明文缓存、拆成多个加载器或只加载首个 DEX。这些会改变保护边界、类型身份或类依赖解析，需独立设计。构建侧缩小不必要的 Payload、减少无用 DEX 可以评估，但不得随意把业务移入壳或破坏现有 allowlist/R8 边界。

### 12.5 实施顺序与验收

| 顺序 | 改造 | 主要验证 |
| --- | --- | --- |
| S1 | 精确分配读取，保留有界兼容与全部校验 | 短读/截断/超长/重复 entry；大 Payload Java 堆峰值及启动时间 |
| S2 | 每 APK 一次 native 扫描，去掉全量 List | ABI 优先级、split、JNI 路径等价；扫描耗时和分配量 |
| S3 | 合并主 APK 扫描、冻结本次路径元数据 | APK 身份、失败缓存与路径一致性；正常启动和错误归属不变 |
| S4 | 最终产物不压缩 Payload 实验 | APK/AAB 实际 entry 方法、包体、冷读性能和解码结果 |
| S5 | 解密/摘要及清理实验 | 各系统 Provider 的耗时、峰值内存、认证失败和清理行为 |

每个实验对比 telemetry 关闭和启用两组，并固定设备、build、Payload、冷/热启动条件及样本量。记录 P50/P95/P99、GC、Java/native 峰值、各阶段异常次数；耗时优化与缺口归因分开验收。第一批不新增运行依赖，不改变加密协议，不减少校验。

建议 S1、S2 与可靠性 P0 并行排期，但拆分提交和性能测量，以便判断改善来自读取/扫描还是上报改动。其余项目以实测结果决定是否推进。
