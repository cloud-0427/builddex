# 07. 服务端性能优化方案

## 目标与范围

当前服务保持 Go 标准库 `net/http`、单体部署和“每家公司一个 SQLite 文件”的架构。本轮不迁移 Gin，不引入 Redis、MySQL 或独立对象存储，优先减少 SQLite 写放大、无界查询、同步日志和长期空闲数据库连接带来的开销。

线上当前暂时使用 `integrityMode=disabled`。这是过渡部署策略，不代表可以使用开发默认密钥：生产环境仍必须注入独立的 `JIAGU_ADMIN_TOKEN` 和随机 `JIAGU_MASTER_KEY_B64`。后续启用 Google Play Integrity 时，需要重新评估外部调用的超时、并发、重试和熔断策略。

## 优化原则

- 先建立基线，再根据指标优化，避免仅凭路由微基准判断整体性能。
- 优先实施可回滚、低复杂度且能减少数据库写入或资源占用的改动。
- 不通过盲目增加 SQLite 连接数提升吞吐；同一个数据库仍然只有一个写入者。
- 所有列表接口必须有确定的单页上限，后台任务必须能随服务优雅退出。
- 每项优化分别提交和验证，避免一次修改多个关键路径后无法定位回归。

## 当前主要瓶颈

### 优化前：SQLite 写入竞争

Challenge 创建曾同时执行过期记录清理和插入，正常请求也会承担清理成本。现已将清理移入后台小批量任务。Release 状态、授权计数和审计记录仍然需要 SQLite 写锁，高并发时需要持续观察等待时间。

### 优化前：无界列表查询

Release 和企业列表现已分页。企业列表仍需扫描目录计算总数，但只打开当前页对应的数据库。

### 优化前：数据库句柄长期缓存

Manager 现已使用租约记录活动请求，并按最近使用时间和容量上限关闭空闲数据库。活动租约对应的数据库不会被后台回收。

### 优化前：同步访问日志

健康检查的快速成功响应现已跳过访问日志，普通成功响应支持确定性采样；错误和慢请求仍完整记录。

## 实施阶段

### 阶段 0：异常隔离

- [x] 增加 Recovery 中间件。
- [x] panic 时记录 requestId、方法、路径、panic 值和堆栈。
- [x] 尚未发送响应时返回统一的 `INTERNAL_ERROR` 500 JSON。
- [ ] 增加 panic 次数指标和告警。

Recovery 主要提升故障隔离能力，不以提升吞吐为目标。

### 阶段 1：低风险快速收益

#### 1. Challenge 后台清理

- [x] 创建 Challenge 时只执行 INSERT。
- [x] 服务启动后运行单个后台清理循环，默认每 5 分钟执行一次。
- [x] 每个已打开企业数据库每轮最多删除 500 条过期记录，避免长事务持续占用写锁。
- [x] 清理失败只记录错误并在下个周期重试，不导致服务退出。
- [x] Shutdown 时通过 context 停止清理循环。

建议监控：Challenge 总数、单次删除数量、清理耗时、清理失败次数和 SQLite busy 次数。

#### 2. Release 和企业列表分页

- [x] Release 列表默认 `pageSize=20`，最大 `pageSize=100`。
- [x] 使用 `(created_at, release_id)` 游标分页，保证时间相同时顺序稳定。
- pack logs 后续从深分页 `OFFSET` 迁移到游标分页。
- [x] 企业列表增加分页，避免一次打开全部企业数据库。

#### 3. 调整访问日志

- [x] `/healthz` 和未来的 `/readyz` 不记录快速成功请求。
- [x] 4xx、5xx 和慢请求完整记录。
- [x] 普通 2xx/3xx 请求支持采样，采样比例通过配置调整。
- [x] 增加慢请求阈值，默认 500 ms。
- 容器化部署优先输出 JSON 到 stdout，由平台完成采集与滚动。

#### 4. 回收空闲数据库连接

第一阶段已采用以下保守默认值，仍需通过压测确认：

```go
db.SetMaxOpenConns(2)
db.SetMaxIdleConns(1)
db.SetConnMaxIdleTime(5 * time.Minute)
db.SetConnMaxLifetime(30 * time.Minute)
```

这些数值是初始方案，不是固定结论。需要比较变更前后的连接等待、SQLite busy、吞吐和 p95 延迟；如果单企业读并发较高，可以单独调整 `MaxOpenConns`。

### 阶段 2：数据库 Manager 扩展性

- [x] Manager 的全局锁只保护数据库句柄、租约和协调锁映射。
- [x] 数据库文件检查、打开、Ping 和 Schema 校验移到全局锁之外。
- [x] 使用按 companyId 的协调锁，避免同一数据库被重复初始化。
- [x] 使用有容量上限的最近使用回收策略；默认最多缓存 128 个企业数据库，空闲 15 分钟后可关闭。
- [x] 通过租约活动计数保证正在被请求使用的数据库不会关闭。
- [x] 企业列表读取失败时通过 `failures` 返回部分失败信息，不再静默跳过。

### 阶段 3：观测与压力验证

至少增加以下指标：

- HTTP 请求量、状态码、p50/p95/p99 延迟和进行中请求数。
- 每企业数据库连接池的 Open、InUse、Idle、WaitCount 和 WaitDuration。
- SQLite busy/locked 错误次数与事务耗时。
- Challenge 创建、消费、过期和清理数量。
- Release 创建、发布、授权以及配额冲突数量。
- 日志写入错误、panic、进程内存、goroutine 和文件句柄数量。

压测场景至少覆盖：

1. 单企业高并发 Challenge 创建与消费。
2. 同一 Release 并发授权和配额扣减。
3. 多企业均匀访问，观察数据库句柄是否稳定。
4. 大量 Release 下的首屏和深分页查询。
5. 慢磁盘、SQLite busy、日志目录不可写和优雅停机。

## 初始验收标准

具体数值以部署机器的基线为准，第一轮可以采用以下工程目标：

- 固定压测负载持续运行 30 分钟，吞吐不随时间下降。
- 稳态文件句柄和内存不随访问过的企业数量无限增长。
- 正常负载下不出现 SQLite locked/busy 对外错误。
- 列表响应的内存占用由 `pageSize` 限定，不随总记录数线性增长。
- Recovery 测试、并发配额测试和 Challenge 单次消费测试全部通过。
- 优化后相同压测场景的 p95 延迟不高于基线，并记录吞吐、CPU、内存和磁盘 IO 对比。

## 暂不实施

- 不为路由性能迁移 Gin。当前主要耗时来自数据库、密码运算、JSON 和日志，路由层不是主要瓶颈。
- 不直接扩大 SQLite 连接池。
- 不在没有基线数据前引入缓存中间件或拆分微服务。
- 不在本阶段改变每企业一个 SQLite 文件的数据隔离模型。
